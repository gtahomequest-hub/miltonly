## What was built

**1. The 90-day password.** `src/lib/portal/passwordRule.ts`: `PASSWORD_MAX_DAYS = 90`, `passwordExpiresAt`, `passwordExpired` (true at 90 × 24 h and after), and `vowStepsLeft` now owes `needsPasswordRenewal` when the password is that old, or has a hash with no `passwordSetAt` (fail closed). The login still signs the person in with the old password (refusing would only send them to the link path, which ends at the same card); no record shows until the card takes a renewal: the same password typed again reconfirms it (hash unchanged, `passwordSetAt` reset) and a different one is judged and replaces it. Proven on localhost: a password backdated 91 days met "Renew your password", the same password reconfirmed, `passwordSetAt` moved to now and the bcrypt hash was byte-identical before and after.

**2. The 60-minute inactivity timeout.** One cookie still (`miltonly_session`, so the battery's `vow-fields` check keeps working), one JWT with two claims: `exp`, the 90-day ceiling fixed at sign-in, and `act`, the instant the session stops counting as active, 60 minutes after the last touch. `getSession()` refuses a token whose `act` has passed (`judgeSession`: expired beats inactive beats ok); `touchSession()` re-issues the token with a new `act` and the original `exp`, from `/api/auth/me` (which `UserProvider` fetches on mount and, since the review, on every client-side navigation) and from every authenticated route. A server component cannot set a cookie in Next 14, so a page render alone does not touch. Every session minted before this deploy carries no `act` and is judged invalid: every signed-in consumer signs in again once (there are two such rows, both the desk's). Proven on localhost with tokens minted by `auth.ts`'s own signer: a fresh token answered `/api/auth/me` with the user and a re-issued cookie whose `exp` was unchanged; a token with `act` in the past answered `user: null` and no cookie; a token past `exp` the same.

**3. Credential records, 180 days, and the "current password" question.** `CREDENTIAL_RETENTION_DAYS = 180` and `credentialRetainUntil()` (expiry plus 180 days) in `passwordRule.ts`; the purge script refuses any row with a `passwordHash`; no other delete path for `User` exists in the codebase; `/privacy` states the rule; `VowConsent` and `VowAccessLog` cascade with the row (so a future erasure path must anonymise, MP-003). **The password is stored as a bcrypt hash (cost 12), never in plaintext, and nothing in this slice changes that.** Appendix B(b) says "username and current password". What we can produce for PropTx on request is the name, the email, the username (the email) and the password *record*: the hash, its set date, its expiry, and the fact that the consumer proved it at each sign-in. A plaintext password cannot be produced. **For Aamir to raise with PropTx:** whether "current password" means the credential as held (a one-way hash, which is what PIPEDA's safeguard principle and every board's own systems expect) or the plaintext. If PropTx insists on plaintext, the answer should be reversible encryption under a brokerage-held key with the trade-off stated, not this slice; nothing here should be weakened silently.

**4. One email, one username and password.** Confirmed and now asserted: `User.email @unique` in the schema, `normalizeEmail()` on the signup, login and verify doors, one upsert by email. Two addresses that Gmail treats as one inbox (dots, plus-tags) are two usernames on this site; the rate limit collapses them (ML-005), the identity does not.

**5. The terms at version 4.** `src/lib/vow-acknowledgement.ts` holds `VOW_TERMS_CLAUSES`, ten numbered clauses in the Appendix's order (i to ix, then the sign-in sentence), `VOW_TERMS_VERSION = 4`, and `VOW_ACKNOWLEDGEMENT_TEXT` as the numbered, newline-joined text stored verbatim. Clause (ix) is bold on the card. `/privacy` gained a bold paragraph naming PropTx and TRREB, auditing and legal purposes, and the 180-day rule; `/terms` states the expiry, the timeout, the registrant rule and the log. Re-consent: `termsCurrent()` requires `vowAcknowledgementVersion >= 4`; a row that agreed to an older text sees "The terms have changed" with the terms and the tick only (plus the registrant question if unanswered); the earlier agreement (text, time, IP, browser) is carried into `VowConsent` before the new one, once; the User row holds the latest. Proven on localhost: a row set to version 3 met the changed terms, agreed, and its history held both agreements; the desk's own row (version null since MP-002b) did the same by link, its password untouched.

**6. The audit trail.** `VowAccessLog` (who, when, kind, scope, path, record count, IP, user agent), written by `logVowAccess()` in `src/lib/vow-audit.ts` after the gate on **eight** surfaces: the street sold-records route, `/api/sold`, `/api/sold-stats`, the listing VOW route, `/api/auth/saved-listings`, the `/listings` grid page, the `/sold` page, and `VowGate` (rendered nowhere in street v2 today). The review found the grid and saved-listings serving VOW-only fields with no row; both write now, and the prebuild walks `src/` for every file that calls `canSeeVowRecords` and fails if one does not write. The write is awaited and never blocks a page (a failure is logged). Export: `/api/admin/vow-access?from&to&format=csv` behind the admin cookie (JSON otherwise, `?view=suspicious&days=N` for the review list, window capped at a year, formula-shaped cells neutralised), and `scripts/export-vow-access-log.ts` from a shell with the same columns. Proven: the test row's first read wrote `street-records farmstead-drive-milton n=12 ip=::1`.

**7. Bona fide and commercial-use controls, the lightest that holds.** (i) The card asks "Are you a licensed real estate registrant?" whenever unanswered; a yes is stored on its own (no password, no agreement), sets `reviewFlag: "registrant"`, and the person meets a wall ("This VOW is for consumers ... email Aamir"); an answered registrant cannot clear it by posting again; only a person clears it (the state script, by hand). Proven on localhost: yes → stored, flagged, listed by the review list, walled on the next sign-in; cleared by hand → records again. (ii) A verified email, the affirmative agreement to the nine clauses, the registrant answer, and the password. (iii) After each trail write, `flagIfSuspicious()` counts the person's last 24 hours with two aggregate queries (over 40 distinct scopes or 400 reads sets `reviewFlag: "suspicious-access"`, once; a flagged person is not re-counted); **that flag refuses nothing**, it puts the person on the review list (`?view=suspicious`, `--suspicious`) for Aamir to judge. Nothing in this slice refuses a real person without a person's review: the only refusal is the consumer's own "yes".

**8. PropTx access, if asked.** Two things, both live now: the audit-trail export (the CSV for the window they name, from the admin route or the shell script, sent by Aamir), and the site itself, which they may register on as any consumer does (clause viii authorises it); the trail then shows their own reads. If they want to watch live, an auditor account is a normal account whose email Aamir knows; the export's `email` column names it. No API key or dashboard was built; the export answers "provide all such information to PropTx upon request".

## Open, every gap not fixed

1. **The battery's sign-in user** (`scripts/verify/checks/vow-fields.mjs`, Core's) is the desk's real row: it must be current on the terms and answer the registrant question (done today) and its password expires **2026-12-19**; the check cannot renew it and picks the most recently acknowledged real consumer, so its reads land in that consumer's trail. A dedicated battery account whose card the check completes itself is Core's change; until then, the desk renews on the card before 2026-12-19, and after any future version bump.
2. **Every existing session signs out at deploy** (no `act` claim) and every existing row owes re-consent and the registrant answer. Two rows exist, both the desk's, both current now. Intended, stated here.
3. **The "current password" wording** (item 3 above): raise with PropTx; nothing changes until they answer.
4. **Three clause wordings** depart from the Appendix's phrasing where the Appendix's own text is not in the repository (the task's summary was the source): (iv) "otherwise use the data" is "otherwise use any of the data or information provided"; (viii) "verify compliance and monitor display" is "verify compliance with the MLS® rules and policies and to monitor the display of Members' listings"; (ix) names PropTx and the site's privacy page. Aamir should read the ten clauses against the document once before 2026-10-01; a change is a version bump, a hash update in the test, and a re-consent for everyone.
5. **The registrant control is self-attestation.** A registrant who answers "no" is a consumer to this code; the tracking (iii) and Aamir's review are the second line. No domain heuristic was built (refusing a real person on a guess is the thing the task forbade).
6. **A renewal on a link-made session** replaces the password without proving the old one: the email is the proof, as it is for every link sign-in. A "change my password" surface (proving the old one) and a "forgot" path that resets before day 90 are MP-003.
7. **Account deletion and anonymisation** do not exist (`/privacy` now says deletion is handled by hand); `VowConsent` and `VowAccessLog` cascade with the User row, so a future erasure path must keep the 180-day records. MP-003.
8. **The response time** distinguishes a refusal (no I/O) from a served read; the body does not. Pre-existing for the honeypot.
9. **`JWT_SECRET` falls back to a dev string** when unset; production has it set. Pre-existing.
10. **`recordCount` means different things per kind** (rows served; 1 for a listing; the 90-day sale count for `sold-stats`; 0 for `VowGate`). Stated in the schema comment.
11. **A person reading one rendered page with no requests for 61 minutes** is refused on the next request: consistent with R-8.13, stated here so nobody reads it as a defect.
12. **`gtahomequest+mp006@gmail.com`** is a second row of the desk's, made for these proofs, with a password and a trail; under the 180-day rule it is not deleted. Aamir may keep it as the dedicated battery account (item 1) by setting `VERIFY_PORTAL_PASSWORD` to its password.
