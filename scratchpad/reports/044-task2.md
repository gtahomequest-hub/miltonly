### Blocker 1 — `burnhamthorpe-road-milton`: no data exists

`getStreetStats()` returns `null`, so `generateStreetContent` throws `No stats available` before it writes anything. That gate (`streetDecision.ts:127-134`) returns null only when **all five** sources are empty, and they are: 0 active listings, 0 sold, 0 active leases, 0 DB3 `sold_count_12months`, 0 `leased_count_12months`.

**Pre-existing, and nothing to do with the rename.** `scripts/regen-results-20260526-002813.json` records the identical `"No stats available"` for this slug on 2026-05-26 — months before DEC-NAME-SOURCE. The function keys on `streetSlug` alone; no name reaches it.

It is `status=published` with a `generatedAt` of 2026-04-22, so a page with no underlying data is live and cannot be repaired by regeneration. That is a decision for you, not a bug I should route around.

### Blocker 2 — `parkway-drive-milton`: the grounding validator will not pass it

**20 attempts across 4 separate runs, every one rejected for `superlative`** — `@market`, `@amenities`, `@about`, `@aha`. Not transient: the same violation class every time.

I did not weaken, bypass, or special-case the validator. It is refusing copy it considers ungrounded, which is exactly its job; whether the `superlative` rule is too strict for a thin street is a separate call and yours to make.

### The two failures that *were* transient

`kennedy-circle` failed once (`numeric_ungrounded` then `methodology_leak`, 5 market attempts) and passed cleanly on retry. `main-street` failed twice — `invented_cross_street` ×5, then a network `fetch failed` — and passed on the third. Both are stochastic. Worth noting the failed attempts left the existing rows untouched: kennedy still read `name="Kennedy Cir W" generatedAt=2026-06-28` after its failure, so a failed generation is not a destructive one.

## One thing I found that you should see

Production served **stale cached pages** through this whole task, and it confirms the Task 1 diagnosis directly rather than by inference.

After bronte-street regenerated at 06:47 with 0 directional occurrences in the DB, the live page still read:

```
<p class="s-character">Bronte Street South ru…
X-Vercel-Cache: HIT   Age: 1424   (cached ~24 min BEFORE the regeneration)
```

Title and H1 were already correct because they come from the resolver; the subtitle is derived from the stored description, which had changed. Same build, same code — purely a CDN-cached render. This is the mechanism I described in Task 1, caught in the act.

Note the limit that implies for step 9: a SHA gate catches *wrong deployment*, not *right deployment, stale page*. It would not have caught this one.
